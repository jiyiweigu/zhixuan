## 一、为什么是这个方案（三条路都被堵）

| 常规方案 | 结果 | 原因 |
|---|---|---|
| 官方安装器 / winget | ❌ | **无管理员权限**（`net session` 失败），系统级安装不可行 |
| Docker / Podman | ❌ | 本机**未安装**，且同样需要管理员权限 |
| EnterpriseDB 免安装二进制包 | ⚠️ 可用但不选 | 下载可达（275MB），但**不含 pgvector**；Windows 下 pgvector 无预编译包且**本机无 MSVC**，无法自行编译 |
| **conda-forge 二进制包（micromamba）** | ✅ **采用** | 免管理员、纯解压即用；`postgresql` 与 `pgvector` **均有 win-64 预编译包** |

> micromamba 单文件（4.6MB），无需安装，不污染系统 PATH。

### ⚠️ 关键限制：本机启动方式

本机 **WorkBuddy 沙箱会回收命令结束后残留的进程**，因此**不能在沙箱内启动常驻服务**：

- `schtasks.exe`（任务计划）被本机**安全策略列入程序黑名单**，不可用；
- WMI 进程创建、`CREATE_BREAKAWAY_FROM_JOB` 均被沙箱拦截；
- 已实测：沙箱内启动的 postgres 在命令结束后即被回收。

**⇒ 服务需在沙箱之外启动一次**（双击 `start_pg.bat`，或在资源管理器中运行）。
已把 `start_pg.bat` 放入**登录启动目录** `…\Start Menu\Programs\Startup\zhixuan-pg16.bat`，
**下次登录 Windows 会自动启动**；若不想自启，删除该文件即可。

> 卸载/清理：停止服务后删除整个 `C:\Users\lenovo\.pg16` 目录，并删除启动目录里的 `zhixuan-pg16.bat`。

### 执行方式说明（重要）

本机 `psycopg` 无法使用（见第六节），故 A5 采用**等价路径**完成：

```bash
# 1) 用 alembic 离线模式生成完整 DDL（不连数据库，仍由 ② 的迁移脚本产出）
cd backend
ZHIXUAN_DATABASE_URL="postgresql+psycopg://zhixuan:change-me@127.0.0.1:5432/zhixuan" \
PYTHONIOENCODING=utf-8 "<pyenv>/python.exe" -m alembic upgrade head --sql > schema_full.sql

# 2) 由 psql 执行（产物与在线 upgrade 等价，并写入 alembic_version）
psql -h 127.0.0.1 -U zhixuan -d zhixuan -v ON_ERROR_STOP=1 -f schema_full.sql
```

> ⚠️ 注意 `PYTHONIOENCODING=utf-8`：不加会让 DDL 里的中文注释按 GBK 落盘，
> `psql` 以 UTF8 读取时报 `invalid byte sequence for encoding "UTF8"`。

> ⚠️ **离线模式的已知局限**：`alembic upgrade head --sql` **不生成 `COMMENT ON` 语句**，
> 首次执行后 `alembic check` 会报 **132 处 `modify_comment`**（**纯注释差异，零结构性差异**）。
> 已用 `C:\Users\lenovo\.pg16\apply_comments.py` 按 `Base.metadata` 补齐 **166 条列注释**，
> 补齐后 `alembic check` 返回 **rc=0 / No new upgrade operations detected**。
> ⇒ 建议：**迁移一旦修好 PG 兼容性，生产/团队环境应改用在线 `alembic upgrade head`**，不要用 `--sql` 模式建库。

## 五、★ 发现的 PostgreSQL 不兼容（**共 8 处**，必须反馈 ②；迁移只在 SQLite 上验证过）

**在线 `alembic upgrade head`（全新空库）实得第一处错误：**

```
sqlalchemy.exc.ProgrammingError: (psycopg.errors.DatatypeMismatch)
  column "master_phd_points" cannot be cast automatically to type json
HINT:  You might need to specify "USING master_phd_points::json".
[SQL: ALTER TABLE school_profile ALTER COLUMN master_phd_points TYPE JSON ]
```

| # | 迁移:行 | 语句 | PG 报错 | 修法 |
|---|---|---|---|---|
| 1 | `0004:30` | `ALTER COLUMN master_phd_points TYPE JSON` | `column cannot be cast automatically to type json` | 加 `postgresql_using='master_phd_points::json'` |
| 2 | `0004:38` | `... WHERE master_phd_points NOT LIKE '{%'` | `json` 类型不支持 `LIKE` | 把该 `UPDATE` **提到类型转换之前**（此时列仍是 VARCHAR） |
| 3–8 | `0006:47 / 146 / 147 / 148 / 176 / 180` | `sa.Boolean(), ..., server_default=sa.text('0')`，**共 6 处** | `column is of type boolean but default expression is of type integer` | 改 **`server_default=sa.false()`**（PG 渲染 `false`、SQLite 渲染 `0`，双方言通吃） |

**性质**：均属 **SQLite 类型宽松、PostgreSQL 类型严格**导致的差异。
`0004` 与 `0006` 迁移**从未在 PostgreSQL 上跑过**——这是 A5 的**真实阻塞点**，不是环境问题。

**补丁已实测可用**：套上上述修复后，在**全新空库**上
`upgrade head` ✅ / `downgrade base` ✅ / 再次 `upgrade head` ✅（往返闭环），
且产物与当前 `zhixuan` **结构零差异**（356 列 / 88 索引 / 96 约束 / 26 序列）。
补丁原文 → `data/在线迁移PG兼容补丁_徐.diff`；逐项证据 → `data/在线迁移复验报告_徐.md`。

**建议**：② 把补丁应用进 `backend/alembic/versions/` 后，③ 再对全新库复跑一轮；
并把这 8 处纳入**迁移回归检查**（至少在 PG 上跑一次 `upgrade head` + `downgrade base`）。

> 本次复验**未改动仓库内任何迁移文件**（`backend/alembic/versions/*.py` 保持原样），
> 补丁只应用于沙箱副本 `C:\Users\lenovo\.pg16\verify_alembic\`。

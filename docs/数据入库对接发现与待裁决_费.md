## 二、需要裁决的口径问题

### 1. 录取分 `batch` 仍未归一为 `batch_code`（阻塞推荐候选）

- **现象**：库内 `school_major_score.batch` 是原始中文值，共 6 种：`本科批` / `本科` /
  `本一` / `本二` / `本科一批` / `本科二批`；`app/models/constants.py` 的
  `BATCH_ALIAS_TO_CODE` 只覆盖「本科批 / 普通本科批 / 本科批次」→ 只有 2025 两省能归一到
  `undergraduate_regular`。
- **影响**：`data/scripts/import_major_score.py` 的注释明确「**不得合并批次**」（本一/本二
  批次线不同、投档序列不同）。因此 2022 / 2024 的录取分无法用于冲稳保分档——
  跨批次取最低分会让 600 分考生看到二本院校的「保」档。
- **当前做法**：推荐候选只取 `batch_code == undergraduate_regular` 的行（即 2025 河南/江西）；
  老高考年份回落演示数据，并在 `data_note` 里写明原因（见 `app/services/candidates.py`）。
- **待裁决**：③ 是否按契约 §8.3 把 `本一/本二/本科` 收敛为 `batch_code`（建议保留
  `undergraduate_regular` + `batch` 展示名两列，批次线通过 `score_segment` 区分）？
  归一后推荐即可覆盖 2022/2024。

### 2. `major_id` 的两种口径：文件侧是「专业代码」，库内是整数外键

- **现象**：`data/scripts/backfill_major_id.py`（③ 的脚本）把 `major_id` 写进 JSON 文件，
  取值是**专业代码字符串**（6/7 位，专业类 4 位）；而库表 `school_major_score.major_id` 是
  **指向 `major.id` 的整数外键**。两者不同源。
- **风险**：若把带代码的合并数据直接喂给导入器，`int_of("010101")` 会得到 `10101`，
  既不是专业代码也不是合法外键，会造成**假挂接**。
- **当前做法**（库侧已实现，见 `app/services/importers/major_links.py`）：
  1. 导入器不再把文件里的 `major_id` 当可变字段（否则二次导入会重置挂接结果）；
     文件值解析不到库内 `major.id` 时按 NULL 落库，**不因此丢行、不猜 id**；
  2. 由 `import_major_links` 按**专业名**挂接：精确匹配 → 零歧义归一（去空白/换行、全角括号
     转半角）→ 否则保持 NULL，不做同义词推断；
  3. 实测结果：**113,836 行命中**（其中按专业类招生 10,817 行）、**2,200 行保持 NULL**
     （试验班 509、理科试验班 143、职业本科专业如「大数据与会计」等，属客观缺失），
     与队长《数据整合与装载交接》§二 的「1.90% 未解析」完全一致。
- **待裁决**：③ 文件侧的 `major_id` 是否改为「与库一致的整数 id」或直接不再写该字段
  （交给装载层挂接）？避免同名字段两套语义。

### 3. `major` 表缺「特设 / 国控」列

- **现象**：`majors.json` 带 `is_special`（493）/ `is_state_controlled`（154）/ `code_len` /
  `code_type`，`major` 表无对应列。
- **影响**：产品端若要提示「国家控制布点专业」（如临床医学、法学等有招生规模限制），
  当前查不到。
- **建议**：加两列布尔位（`is_special` / `is_state_controlled`），代价极小；
  在此之前不入库，仅报告登记。

### 4. 专业目录的层级怎么用

- `major` 表只有一个 `category` 列，而目录有「学科门类（12）/ 专业类（93）/ 专业（845）」三层。
- **当前做法**：`category` 存**学科门类**（`/api/majors?category=` 的语义词是「学科门类精确匹配」）；
  93 个专业类作为 `is_category=True` 的行一并落库（专业类名是录取分里真实出现的「按类招生」条目）；
  专业 → 专业类的从属关系用 **代码前 4 位** 表达（`080901` → `0809`），不额外落列。
- **待确认**：产品端是否需要「按专业类筛选专业」的接口？需要的话建议加 `class_code` 列而非
 再塞进 `category`。

### 5. 录取分 `school_id` 空值规模差异

- 本地按③的院校库重建后：`school_id` 为空 **2,305 行**（命中 98.0%）；队长合并版为 **1,983 行**。
- 差异来自整合期重做的院校映射（③ 原始导出 2,862 行未挂上，归一化后 2,500 上下）。
- **待裁决**：等 merged 数据集分发后以队长版本覆盖一次即可；在此之前不影响接口（NULL 行如实留空）。

### 6. `data_status` 的判定口径（供接口层统一）

- 事实数据（录取分 / 一分一段）：库内有真实数据 → `available`；无匹配版本 → 如实说明。
- 基础字典（专业库）：核心字段有、扩展字段（`intro` / 一流专业建设点院校）无来源 → `partial`。
- 演示回落（冲稳保候选）：`schema_only`，且必须在 `data_note` 说明「演示数据（非官方）」。

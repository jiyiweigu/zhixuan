## 任务要求

1. **以契约 v1.4 为唯一依据**，逐一核对管理端 5 个 section 的取数形状：
   - 对照 `frontend/src/api/index.ts`、`frontend/src/types/`、`frontend/src/mocks/` 里管理端相关定义与请求；
   - 对照后端 `backend/app/api/v1/admin/rules.py` 的真实路由与响应 DTO；

2. **替换 Mock 为真实 API 调用**：保留 mocks 目录作为离线开发兜底（可切换），但默认走真实接口；错误处理按契约的错误码结构（含 `3001` 规则缺失类错误的专门提示文案）。
3. **审核闭环体验**（产品「可信机制」卖点在管理端的呈现）：审核 section 展示 `review_task` 队列（T3 之后会有真实低置信问答流入），支持逐条「采纳/驳回/修改后采纳」，操作走契约定义的接口；若后端字段尚未有数据，按契约形状渲染空态。
4. **批量导入**：规则管理 section 支持契约 §8.8 的批量导入（文件上传 + 校验结果回显，行级错误展示——契约若定义了校验响应结构，逐字段对齐）。
5. **统计 section**：用 ECharts 展示契约统计接口返回的指标（如来源数、语料量、审核队列深度等，以契约字段为准）；中国地图类可视化若涉及，**必须使用审批合规的数据源与地图**（本项目试点省份粒度用省份列表即可，避免全量地图合规问题）。
6. **`data_status` 旧值归一**：顺手检查 `src/mocks/` 与 `src/types/` 里残留的旧 `data_status` 取值（`verified|pending`），统一为契约 v1.4 的词表口径。
7. **构建与自测**：`cd frontend && npm run build` 通过、`vue-tsc`（若配置）无新增类型错误；为 5 个 section 各写至少一条关键路径的手测记录（贴 PR）。

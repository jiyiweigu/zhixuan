## Context

当前分支本地工作区是本次事实来源；T4/T5 的数据与改动已在本地，不能依赖远端分支刷新。API 契约是 `docs/api-contract.md` v1.5，普通本科批校验路径为 `/api/eligibility/check` 与 `/api/user/eligibility/check`。现有 SQLAlchemy 模型、管理端规则维护/importer、服务层和纯函数引擎均已存在，基本不需要另建架构。

本地检查发现这些高风险接缝：`_subject_requirements_by_unit` 只按 `major_id` 查询，未消费已有的 `SubjectRequirement.group_code`；`_restrictions_for` 将省份/年份的所有体检规则整体交给引擎，而 `physical_check` 当前逐条遍历，未按当前志愿单位的专业目标过滤。T4 完整文件共 17,492 条规则行：河南 2025 有 9,809 条、江西 2024 有 7,683 条，2026 行为 0；当前目标分母不能从规则文件推导。T5 有 35 条规则，生成器 dry-run 展开 491 条，最初有 14 条标记需引擎扩展；T6 支持 4.5 裸眼视力线后，仍有 13 条规则因 BMI、性别或矫正视力字段限制不能安全求值。通用 importers CLI 未装载选科/体检，但管理端 `rule_admin.import_rule_dataset` 是已存在的 500 条事务导入通道。省份模板 JSON 已有江西 2026 行，仍须检查其 `exam_type` 等值是否能被 importer 接受。纯函数基线测试为 `test_constraints.py` 41 项、`test_engine.py` 34 项。

## Goals / Non-Goals

**Goals:**

- 让服务层从现有数据库规则表组装按省份/年份/批次/考试类型及单位目标隔离的规则快照。
- 令专业组级和专业级选科要求都能命中，缺失/未解析目标按契约拒绝产生肯定结论。
- 将体检限制精确应用到当前单位的专业/专业类，并把未支持的条件、阈值或分类留在 `unknowns`。
- 维持四闸门顺序、纯函数边界、来源三要素、`eligible` 三态、错误码及 API v1.5 DTO。
- 以可重复计算的报告说明 2026 真实覆盖现状，帮助团队判断接真实数据后的演示边界。
- 对不能由当前档案字段安全判定的性别/BMI/矫正视力等条件只生成 unknown；不扩展档案字段，也不猜测性别或用裸眼视力替代矫正视力。

**Non-Goals:**

- 不重写规则 CRUD、导入框架、数据库模型或前端体验。
- 不将江西 2024、河南 2025 或 mock 数据补作 2026 正式规则。
- 不承诺现有数据已覆盖两省所有院校专业；数据缺口按契约显式暴露。
- 不扩展艺术、体育、提前批、高职规则验收范围。
- 不修改 API DTO 或更改 `docs/api-contract.md`；若发现契约阻碍实现，应暂停该处并先提出契约变更。

## Decisions

### 1. 保留分层：查询/组装在 service，判定在纯函数 engine

Service 负责解析请求目标、读取 SQLAlchemy 模型、核对 `RuleDatasetStatus` 与来源，并把不可变字典/序列传给 engine。Engine 不导入 DB、HTTP、文件系统或大模型模块。四闸门仍按省份规则 → 选科 → 体检 → 学费执行。

**替代方案：**在引擎里直接查库或让 API 端点内写判定。前者破坏已有架构红线与离线可测性；后者重复业务逻辑、容易让游客和登录接口行为分叉，因此不采用。

### 2. 以请求目标键构造规则索引，先验证覆盖再运行整批校验

每个单位以 `unit_id`、`school_id`、`group_code` 和 `major_ids` 建目标集合。选科规则优先按省份代码、年份、学校及专业组定位组级行，同时读取该单位实际专业的专业级行；组级行用于整个一致要求的专业组，专业级行用于细粒度要求。对未覆盖的实际目标先生成结构化缺失清单，再按 API 已定义的规则返回 `3001`，错误信息包含受影响单位和目标；不返回部分单位的成功资格结果。`missing`、`unparsed` 不能作为明确不限处理。旧考试制度只有在当年省份规则明确表示无选科模式时，才按既有产品语义说明，不以缺记录推导。

**替代方案：**每条专业始终强制要求专业级记录。该方法会拒绝合法的组级要求并与 T4 行粒度冲突，不采用。静默跳过找不到要求的专业则会违反 `3001` 红线，也不采用。

### 3. 体检规则按目标过滤，未知映射保留待核验

Service 载入相同省份/年份及全国适用规则，并保留 `major_code`、`major_category`、条件、阈值、级别和来源。引擎接收当前单位实际专业的稳定代码/已确认类别，只将精确适用规则传入条件判定；既无精确匹配又无法证明无需映射时，生成带目标与缺失字段说明的 unknown。军队/公安专属规则仅在对应 `pathway_id` 下参与判定，不能应用到普通志愿。匹配到的档案缺项仍是 unknown；只有条件、阈值和来源均可解释时才产生 blocker/warning。

**替代方案：**把同省所有体检规则应用到所有专业。当前代码路径接近此做法，会产生误拦截和错误提示；不能保留。单靠展示名称模糊匹配会因同名/类别漂移而误判，故稳定代码优先，类别只能使用经数据字典确认的映射。

### 4. 把规则覆盖分成“规则集状态”和“目标级命中”两层

`rule_dataset_status` 继续表达省份/年份/批次/考试类型级的数据状态；service 另按本次请求逐目标核验覆盖。状态为 `partial`、`schema_only` 或 `unavailable` 的必需规则集不能产生成功资格结论。身体限制的类别映射缺失按契约作为目标 unknown 展示；不得仅因没有命中规则推断“身体无限制”。T4 非 `ok` 行由现有构建器排除，保持目标缺失并进入审计；规则表没有每行 status 字段，因此报告保留源字典状态，不可伪装成库内状态。T5 的 `engine_ready=false` 不可直接落成可判定 blocker/warning：引擎必须基于条件/阈值/档案字段确认能安全比较，否则返回 unknown。可选学费数据保持现有 `unknowns` / `partial` 契约语义。`3001` 响应仍是统一 envelope，并包含 `data_status` 与 `missing_rule_sets`；不新增字段形状，目标信息放入既有错误 message/data 可承载范围。

### 5. 数据对账作为验收产物，不把数据库行数等同覆盖率

脚本/报告应从带版本的 T4 字典及实际 importer 目标键计算分母：去重后的河南/江西 2026 普通本科批有效目标；分别统计 `ok`、`missing`、`unparsed` 与未匹配组，并计算预期触发 `3001` 的目标比例。必须记录数据快照/文件校验值或生成时间、归并规则、排除项；报告应区分“规则行覆盖”与“服务能以当前数据库主键解析”两种比例。仅把已导入行数、规则集 `available` 或演示夹具当作完整率不合格。

## Risks / Trade-offs

- [现有 T4 字典的组级 target_id 不一定能映射到数据库 `school_id/group_code`] → 先用只读对账量化键匹配率，再实现明确的归一/导入映射；无法映射的行保持未覆盖，不猜测院校或组。
- [专业类/专业代码数据字典粒度与 T5 映射不同] → 先核对导入器及专业主数据字段；无稳定对应时返回 unknown 并列出未映射目标，不做名称宽松匹配。
- [规则状态表可能把“存在记录”误当 `available`] → 按契约以声明状态及目标覆盖共同校验；验收测试覆盖部分状态与缺目标场景。
- [更严格的缺失检查会增加 `3001` 数量] → 对账报告给出分省分母和预计受影响比例，作为团队接入数据的量化清单；不降低门禁规避失败。
- [T6 任务单的旧年份/旧分支描述可能误导实施] → 本方案明确按本地数据和 2026 规则，不执行 checkout/merge，也不提交或推送。

## Migration Plan

1. 先运行指定 Python 环境的既有基线并保存结果；读取本地 2026 字典，生成只读覆盖基线。
2. 先补目标解析与纯函数目标过滤，再接服务层数据库查询/覆盖门禁；保持错误 envelope 和响应 DTO。
3. 通过现有 importer 装载或校验省份模板及规则夹具，验证来源、版本、逻辑键与事务行为；正式数据只导入可追溯已核验记录。
4. 运行新增的引擎、服务/API、导入测试及原 41+34 回归测试；重算并保存最终覆盖报告。
5. 回滚时只撤销 T6 新增/修改文件或恢复其改动；不回滚他人已有工作区修改。无 schema 迁移计划，除非实查证明现有模型无法表达需求，此时另提变更。

## Open Questions

- T4 有 2026 招生目标清单时，再补算该年份真实目标级比例；本地当前没有该分母，报告明确“不可计算”，不使用旧年目标代替。
- 性别目前不在 API v1.5 的 constraint profile 字段中；军警身高/BMI 等按性别阈值在本轮只能 unknown，后续如需确定判定须单独扩展产品/API 档案。

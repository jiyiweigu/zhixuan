## Why

当前档案、资格自检和志愿方案页面尚未覆盖选科、身体条件、学费与省份志愿模板的一体化核验，团队也缺少可由前后端与数据库共同实现的行为规格。现在先冻结普通本科批的功能边界与数据状态语义，使成员可以并行完成页面、规则引擎和数据接入通道；真实规则经数据库成员核实后再导入，数据缺失期间不得产生误导性的“合格”结论。

## What Changes

- 扩展考生档案，支持选科、体检与预算等约束信息的分步采集、增量保存、完整度反馈和未填语义。
- 增加按省份、年份、批次版本化的志愿模板及专业要求查询；首期功能范围为河南、江西普通本科批，提前批只保留扩展能力。
- 提供确定性四闸门校验（省份规则、选科、身体条件、学费）及游客/登录用户批量校验，统一返回硬拦截、软提示、待核验结果和可追溯依据。
- 在资格自检、方案风险体检、专业详情与档案页面呈现规则状态和校验原因；被拦项目可查看，不做静默隐藏。
- 建立版本化规则数据模型、来源校验、数据集状态登记、管理端维护与批量导入通道；真实数据未导入时显式返回未就绪状态。
- 本变更不要求提供或伪造真实招生规则数据，不包含提前批的业务规则实现，也不以估算学费产生正式资格结论。

## Capabilities

### New Capabilities

- `admission-constraints`: 定义版本化规则数据、四闸门批量校验、状态与溯源语义，以及相关用户端和管理端行为。

### Modified Capabilities

- `candidate-profile`: 增加约束字段、两段式录入、增量保存、完整度和 `null` 未知语义，避免档案要求分散到多个能力。

## Impact

- API 契约：`docs/api-contract.md` 第 8 节定义的 Profile 增量字段、公开规则查询/校验接口、管理端规则维护与导入接口。
- 前端：`frontend/src/types`、`api`、`mocks`、Profile/Eligibility/Plan/School/Major 页面、共享结果组件与状态缓存。
- 后端：Pydantic DTO、Profile 服务、纯函数规则引擎、公开与管理端路由、错误码和测试。
- 数据库：版本化规则表、数据集状态表、迁移、来源与唯一性校验、导入入口。
- 团队开发以 API Contract v1.1 为字段基线；如契约与本提案后续规格有冲突，先同步修订契约与规格再实现。

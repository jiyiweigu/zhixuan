## Context

产品已有考生档案、路径资格自检、志愿方案、院校与专业页面，但前端仍以少量演示字段驱动页面。后端当前只有 FastAPI 路由、Pydantic 基础模型和演示资格函数，没有数据库模型、迁移或真实规则数据服务。`docs/api-contract.md` 第 8 节已经冻结约束增量的字段和接口；该文档作为 API DTO 基线。

首期范围是河南、江西普通本科批的完整功能链路和规则数据导入能力，不要求在本变更内获得或伪造官方规则数据。真实规则未到位时，规则查询应报告 `schema_only` / `unavailable`，资格校验应报 `3001`。提前批复用版本化模型的扩展能力，但其规则与业务校验不在首期交付。

## Goals / Non-Goals

**Goals:**

- 在现有 `/profile`、`/eligibility`、`/plan`、院校/专业详情中建立档案录入、资格解释和志愿表风险体检的连贯流程。
- 让前端、后端和数据库共享 API Contract v1.1 的请求、响应、错误和数据状态定义。
- 建立可按省份、年份、批次、考试类型隔离的规则模型、迁移、来源验证和导入/管理通路。
- 以确定性纯函数完成四闸门判定；档案缺项是待核验，规则集缺失不能降级为通过。
- 在无真实数据环境下可通过 Mock 和 schema-only 数据状态开发交互与接口，不把演示结论当成真实规则结论。

**Non-Goals:**

- 本变更不采集、爬取或承诺提供已核实的河南/江西规则种子；由数据成员后续根据官方来源导入。
- 不实现提前批、艺术/体育专项、专科、强基/综合评价等各自的报考业务规则。
- 不使用大模型做任何资格判断，不把估算学费或通用专业类别推断作为官方结论。
- 不重做志愿推荐算法；本变更只对已选志愿单位进行约束检查与风险展示。

## Decisions

### 1. 以既有 API Contract v1.1 为唯一 DTO 基线

新增接口、Profile 字段、`data_status`、`3001/4001` 与管理员接口都按 `docs/api-contract.md` 第 8 节实现；如实施中发现契约缺口，先由队长同步更新契约、OpenSpec 规格与前端类型/Mock，再继续联调。API 继续使用 snake_case 和统一响应包。

**备选方案：**前后端各自按照产品书小节实现。拒绝该方案，因为旧文档存在提前批、预算字段、部分数据降级等冲突，独立解读会导致 DTO 不兼容。

### 2. 数据规则版本化，并显式记录数据集状态

以省份代码、年份、批次、考试类型作为模板定位维度。选科、身体限制、章程要求、学费使用稳定的专业/专业组标识及来源三要素。规则逻辑表以契约 8.7 为准，另设 `rule_dataset_status` 区分 `available`、`partial`、`schema_only`、`unavailable`。即使某项要求明确“不限”，也必须有可溯源的数据记录或状态证明，不能把空表解释成不限。

**备选方案：**把整套规则放入一个无版本 JSON 配置。拒绝该方案，因为无法可靠约束重复项、按专业查询、来源审计或历史版本并存。

### 3. 规则读取与纯函数判定分层

API/service 层按地域、年份、批次和志愿单位读取规则快照，再将不可变输入交给 `app/engine` 纯函数。引擎负责省份模板结构、选科、身体条件、学费与其他明确录入的招生要求的判定，不访问数据库、不请求网络、不调用大模型。服务层统一组装 citations、结果分档与 summary。

**备选方案：**在 FastAPI 路由或前端组件内直接判定。拒绝该方案，因为路径/专业/方案页会产生多套不一致判断，也无法稳定复测。

### 4. 区分考生信息未知与规则数据未就绪

考生字段 `null` 产生 `unknowns`，且令 `eligible=null`（无硬拦截但存在待核验）。规则缺失、部分覆盖不足或当前批次未支持时，规则查询返回状态和缺项；校验端点返回 `3001`，不得以 unknown 或默认通过掩盖服务器数据缺口。只有规则集齐备、每条事实有有效来源时才能把数据状态标为 `available`。

**备选方案：**将规则缺项也返回 `unknowns` 并继续显示其他规则结论。暂不采用，因为部分规则会让已显示的“无 blocker”被误读为安全；未来如需允许部分结论，必须在产品上明确完整性边界后单独调整契约。

### 5. 前端通过 Mock 开发并保留数据状态标识

前端新增 typed API、Mock 和共享约束状态；Mock 覆盖 blocker、warning、unknown、数据未就绪、加载/空/错误状态。真实模式仅消费后端响应，不复制资格算法。Profile 变更后清除过期检查缓存；资格页解释路径/专业结论，方案页扫描整张志愿表，详情页展示专业要求与来源。拦截项目仍可由用户查看原因。

### 6. 规则写入必须可审计、可回滚

使用项目冻结的 PostgreSQL/SQLAlchemy/Alembic 技术路线建立表和迁移。管理端规则维护与数据批量导入均校验年份、地域、稳定目标 ID、枚举及来源；批量导入为事务性操作，任一项失败整批回滚。更正/替换规则时保留版本或审计记录，不覆盖其他年份数据。

**备选方案：**先用硬编码常量或临时内存字典完成线上 API。拒绝该方案，因为导入数据时将需要重写读取与状态判断链路。

## Risks / Trade-offs

- [真实规则尚未到位，无法验证真实判定覆盖率] → 交付 schema-only 管道和显式 `3001`；Mock 只验证交互与 DTO，真实数据导入后按规则验收用例复测。
- [招生规则按省份/年份和专业变化，错配会造成误导] → 每条事实强制来源三要素、目标稳定 ID 和年份；跨省跨年不得回退读取。
- [体检信息敏感且用户可能不愿填写] → 采用可跳过录入、最小必要字段、显式待核验；不采集身份证或原始报告。
- [现有后端尚无数据库/鉴权基础实现] → 本变更先提供迁移与数据访问所需基础；档案登录态使用现有 API 约定，持久化集成须与认证骨架联调。
- [部分规则缺失使全批校验返回错误，降低演示完整度] → 提供 Mock 演示三档结果与单独的未就绪场景，清楚区分演示模式和真实模式。
- [API Contract v1.1 与产品书旧章节存在预算字段、降级和批次范围差异] → 以本次提案采用的 API Contract v1.1 和以下规格为增量基线；实现前将对应产品书内容同步修订，避免两份“唯一依据”。

## Migration Plan

1. 核对 API Contract v1.1 与本规格，生成 DTO/Mock 变更清单并完成数据库迁移设计。
2. 运行 PostgreSQL 迁移，新增规则版本、规则实体与数据集状态结构；初始数据只登记为 `schema_only`，不插入臆造的正式规则。
3. 实现规则仓储/服务、纯函数引擎与公开/管理接口；确认缺数据走 `3001`。
4. 并行完成前端档案、资格自检、方案体检、详情和管理端交互；先用 Mock 验收，再对接真实后端。
5. 后续启用步骤（不阻塞本变更完成）：数据成员导入并核验官方规则后，将对应数据集状态提升为 `available`；执行来源、版本和边界用例复核后开放真实校验。

回滚时可回退应用版本并降级规则数据集状态为 `schema_only` / `unavailable`，避免继续对外产生基于问题数据的结论。数据库迁移的回滚按 Alembic 逆迁移执行；不得删除已审计的历史版本记录。

## Open Questions

- 既有账号/档案认证与数据库迁移骨架尚未出现在当前后端目录中，实际连接配置和迁移环境需由后端负责人按产品书技术栈补齐。
- 身体条件采集字段在 API 契约中已给出；正式上线前仍需由产品/指导老师复核敏感字段的必要性和隐私告知文案。
- 只有在真实规则数据完整性标准与审核责任人明确后，数据集状态才可从 `partial`/`schema_only` 提升为 `available`。

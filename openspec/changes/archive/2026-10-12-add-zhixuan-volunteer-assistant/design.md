# Design

## Context

本产品为 2026 年第十四届全国大学生数字媒体科技作品及创意竞赛参赛作品，须在 2026-10-23 前完成可运行 Demo 与作品材料，团队 5 人、周期约 15 天。目标用户为高考考生与家长，试点省份为河南省（第一）与江西省（第二）。

约束条件：团队为学生团队，无专职运维与美术资源；数据来自公开渠道；作品须可核验、可溯源，并满足竞赛对 AI 工具使用与第三方资源披露的要求。动机与范围见 `proposal.md`，行为契约见 `specs/`。

## Goals / Non-Goals

**Goals:**
- 在 15 天内交付可运行、可演示的完整 Web 应用（用户端 + 管理端）。
- 保证答案可溯源、资格判定可复核、生活信息可标注来源，满足可信与合规要求。
- 架构上支持 26 类升学途径，数据上分层落地，兼顾完整性与交付质量。

**Non-Goals:**
- 不做面向 C 端的移动 App / 小程序（Web 优先，uni-app 适配列为 P2）。
- 不做录取预测的概率建模与承诺性结论。
- 不在首期接入全部省份与全部途径的录取数据。
- 不做商业化（支付、会员）相关能力。

## Decisions

**D1 前端采用 Vue 3 + TypeScript + Vite + Element Plus + ECharts。**
理由：Element Plus 组件完备，无美术基础也能产出规范界面，契合团队构成与工期；ECharts 满足数据可视化。备选 React 生态同样成熟，但组件库的默认视觉完成度需要更多调试成本。已冻结。

**D2 后端采用 Python 3.11 + FastAPI。**
理由：RAG 相关库（Embedding、Rerank、向量处理）以 Python 生态最成熟；FastAPI 自动生成 OpenAPI，支撑前后端契约先行、并行开发。备选 Node.js 在 RAG 生态与模型调用上不如 Python 直接。

**D3 数据与向量统一使用 PostgreSQL 16 + pgvector。**
理由：结构化数据、用户数据与向量共用一个数据库，免去额外中间件与部署运维成本，适合学生团队与中小数据量。备选 Milvus/Chroma 需独立部署，收益有限而成本更高。

**D4 检索采用"向量 + BM25 双路召回 + RRF 融合 + 重排"。**
理由：分数线、位次等强结构化数值需要关键词精确匹配，语义泛化需要向量召回，二者互补；RRF 融合无需调参即可稳健合并；重排提升溯源准确度。备选纯向量检索会在精确数值查询上失准。

**D5 生成采用"受限提示词 + 强制引用"，而非自由生成。**
理由：志愿填报为高风险决策场景，事实错误代价高；受限生成要求模型仅依据检索片段作答，并对每条结论标注引用，无依据时明确回复暂无数据，从机制上抑制幻觉。

**D6 路径资格判定由确定性规则引擎实现，不使用大模型。**
理由：资格判定结果直接影响用户决策且须可复核；规则引擎输出确定、可追溯规则与来源，避免"AI 猜测资格"的合规与准确性问题。大模型仅用于语言问答，不参与资格裁决。

**D7 用户端与管理端为同一 Vue 工程、通过路由与角色权限区分。**
理由：管理端以 CRUD 表单为主，复用同一工程的鉴权、请求封装与组件库，显著降低搭建成本，符合 5 人团队工期约束。

**D8 采用"架构全面、数据分层"策略（P0/P1/P2）。**
理由：竞赛评分关注"选题规模是否合理、目标与成果是否一致"；全量落地 26 类途径数据不可行。故途径字典与规则全量可用，录取数据分层落地，未落地部分在界面与材料中如实标注。

**D9 生活类信息引入 `source_type` 与 `reliability` 字段并分级展示。**
理由：宿舍、食堂等信息主观且多来自非官方渠道，直接展示存在合规与信任风险；通过来源类型与可靠性分级、非官方默认折叠，兼顾信息价值与合规。

**D10 试点顺序为先河南、后江西。**
理由：河南为考生大省，三大专项、艺术科类、军警招飞等路径最典型，且团队负责人为河南籍、熟悉政策与数据渠道；江西作为二期验证跨省可扩展性。

## Risks / Trade-offs

- [范围扩张导致主功能交付不足] → 严守 D8 分层：P0 必成、P1 尽力、P2 仅架构支持并如实标注。
- [数据缺失或年份错误导致结论不可信] → 仅使用已核实数据；缺失展示"暂无"，禁止由模型补全；所有事实表强制记录来源三要素。
- [模型幻觉] → 受限提示词 + 引用溯源 + 置信度分级 + 人工审核四重约束。
- [资格判定错误误导用户] → 规则引擎显式实现 + 规则来源可查 + 边界用例测试 + 免责声明。
- [生活类信息失实] → 来源与可靠性强制标注，非官方信息默认折叠并提示仅供参考。
- [大模型 API 额度或可用性问题] → 提前申请；准备降级方案（返回检索片段原文摘要）。
- [多人协作集成冲突] → 契约先行（D4 前产出 OpenAPI）、分支规范、每日站会、接口变更当日同步。

## Migration Plan

本项目为新建，无历史数据迁移。部署步骤：
1. 初始化 PostgreSQL 并安装 pgvector 扩展，执行建表迁移脚本。
2. 运行数据管道导入试点省份语料并构建向量索引。
3. 启动后端服务（uvicorn）与前端（Vite 构建产物 / 开发服务器）。
4. 创建管理员账号，导入初始途径与规则数据。
5. 回滚策略：保留建表与数据导入脚本可重放；索引重建失败不影响已有索引。

## Open Questions

- Embedding 采用本地 bge-small-zh 还是云端 API：影响部署复杂度与成本，不影响行为契约。
- 首期院校画像的生活信息范围：是否仅纳入官方可核验字段，可在 D2 确定。
- 就业数据是否纳入院校画像：涉及数据口径与合规，可延后决定。
- 江西试点的时序与数据量：视河南数据管道稳定情况决定。
